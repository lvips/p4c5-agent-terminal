## 1. Subagent Context 爆炸（M0-A 5 个调研 subagent 全部失败）

**日期**：2026-09-06
**阶段**：M0-A 5 份 datasheets-summary 调研
**影响**：5 个 subagent 全部停在「调研完成 → 写报告」拐点

### 现象

- 5 个 subagent 几乎同时启动
- 关闭消息为空或残缺（如 "现在去 AT 总览、TCP/IP 实际命令示例部分找关键参数："）
- **无任何 deliverable 文件产出**（5 份 datasheets-summary 全部为空）

### 根因（2 个自述交叉验证）

| 根因 | 证据 | 严重度 |
|---|---|---|
| **Context 爆炸** | Subagent #1：一次性 dump 25,418 行 PDF 文本（p4 13,574 + c5 11,224 + schematic 620）| 🔴 主因 |
| **方法论错误** | Subagent #1 自述："应该 `grep -A1 -B1 "MHz"`，不应该 dump 整本 + `sed -n 'A,Bp'`" | 🔴 主因 |
| **写报告被延后** | 5 个 subagent 全部停在「调研完成 → 写报告」拐点，从未调用 `write`/`git commit`/`report` | 🔴 主因 |
| **图片 PDF 未处理** | Subagent #2：ML307C 硬件规格书是图片型，`pdftotext` 返回 0 行，未 OCR | 🟡 中因 |
| **Bash 参数污染** | Subagent #2 第一次 bash 报 `invalid justification: expected a non-empty sentence` | 🟢 轻因 |

### 修复（已写进 SUBAGENT-BEST-PRACTICES.md）

1. **DSH 端预处理**：派 subagent 前先把 PDF 抽到 `/tmp/<topic>/`，subagent 只 `grep`
2. **新 prompt 模板**：强调"先 `write` 空骨架，再 `grep` 填充"（先有 deliverable）
3. **工作流 4 步纪律**：write 骨架 → grep 填充 → git commit → report
4. **图片 PDF 标注**：pdftotext 无效的标"未 OCR + M1 实测人工补"
5. **Subagent 类型选择**：简单用 `subagent`，重 PDF 用 `subagent_fork` 隔离 context
6. **Bash 警告**：subagent 调 bash 不要带 `sandbox_permissions`

### 教训

> **"先有 deliverable，再做更多调研"**——这条原则同样适用于 M2+ 所有 subagent 任务。

### 兜底

DSH 用自己的工具直接产出 5 份 datasheets-summary（4908 字），M0-A 任务目标 100% 达成。

## 2. PDF 抽取的坑

### 2.1 原理图 PDF（图片型）

- 工具：`pdftotext` 26.04.0
- 结果：620 行乱码（"GND GND C1 C2..." 重复 1000 次）
- 原因：原理图由 `Microsoft Print to PDF` 导出，纯图片
- **解决**：用 PDF 阅读器人工查看，不依赖 `pdftotext`

### 2.2 ML307C 硬件规格书（图片型）

- 工具：`pdftotext`
- 结果：0 行（完全空白）
- 原因：4 页全图片（"图片文档"）
- **解决**：OCR 或人工查阅
- **教训**：未来检查 `pdftotext` 输出行数，0 行立即判定图片型

### 2.3 ESP32-P4 / C5 规格书（文本型）

- 工具：`pdftotext`
- 结果：13,574 + 11,224 行（成功）
- 教训：行数大不代表"内容可读"，**必须用 grep 模式搜，不要 sed 翻页**

### 2.4 ML307C AT 文档（文本型，14 份）

- 工具：`pdftotext`
- 结果：每份 1,388-4,753 行（成功）
- 14 份总计约 30,000 行
- **关键价值**：14 份文档完整覆盖所有协议（TCP/IP / MQTT / HTTP / SSL / FTP / GNSS / LBS / LwM2M / 文件系统 / 拨号 / 通信流程）

## 3. ML307C 固件 ZIP 编码坑

### 现象

`unzip -O` 参数在 macOS 上无效。中文文件名出现 `涓ㄧ嚎IP` 这种 cp437 编码。

### 解决

```python
import zipfile, os

# 解码链
def decode(name_bytes):
    for enc in ['utf-8', 'gb18030', 'gbk', 'big5']:
        try:
            return name_bytes.decode(enc)
        except:
            continue
    return name_bytes.decode('utf-8', errors='replace')

# 解压
with zipfile.ZipFile(zip_path) as zf:
    for member in zf.namelist():
        decoded_name = decode(member.encode('cp437'))
        zf.extract(member, dst_path)
        # 重命名为解码后的名字
        os.rename(os.path.join(dst_path, member), os.path.join(dst_path, decoded_name))
```

### 教训

> macOS `unzip` 工具对 GBK/Big5 编码 ZIP 文件**完全无法处理**。必须用 Python `zipfile` 库 + 显式编码。

## 4. Cordis 插件开发的关键设计

### 4.1 路径常量 vs 全局配置

**决策**：所有路径硬编码到 `code.host.js` 顶部（`PROJ_DIR = '/Volumes/ZT-1T/项目开发/ESP32-P4C5'`）

**原因**：
- 不依赖全局 `~/.dsh/` 配置
- 完全项目本地（可单独 commit）
- 接手者一眼看懂结构

### 4.2 Service / Tool / Timer 三件套

```js
ctx.register('cca.session', ccaSession);  // Service
harness.registerTool(ctx, defineTool({...}));  // Tool
ctx.effect(() => timer.interval(() => {...}, 30000));  // Timer
```

**Service**：提供长驻状态（PID / session-id / alive）
**Tool**：暴露给 DSH 调用的接口（agent_cca / agent_ccb / cc_status）
**Timer**：30s 心跳写入 logs/heartbeat.log

### 4.3 Bash 调用 `cc-dispatch.sh` 而非直接 spawn claude

**原因**：
- `cc-dispatch.sh` 已有 30min 硬超时 + 15min 防停滞 + 启动加固
- 复用而非重写
- 失败模式一致（便于排错）

### 4.4 临时 prompt 文件清理

```js
const tmpPrompt = join('/tmp', `cca-prompt-${Date.now()}.md`);
writeFileSync(tmpPrompt, prompt, 'utf-8');
try {
  execFileSync(...);
} finally {
  try { unlinkSync(tmpPrompt); } catch {}  // 用 try-finally 确保清理
}
```

## 5. OMT 项目不可改（强约束）

- OMT 仓库：`/Volumes/ZT-1T/项目开发/OMT/`
- macs 仓库：`/Volumes/ZT-1T/项目开发/multi-agent-collab-system/`
- DSH 全局：`~/.dsh/` + `/opt/homebrew/lib/node_modules/@deepseek-ai/`

**原因**：
- OMT 是"参考实现"，不能反向污染
- macs 是"协作系统"基础设施，不能动
- DSH 全局是所有项目共享，修改影响所有 DSH 用户

**检查**：本项目所有 commit 都不应包含上述路径的修改（git 历史可查）。
